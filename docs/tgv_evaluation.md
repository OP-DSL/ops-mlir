# Taylor-Green vortex: fusion and reordering evaluation

Generated by `apps/c/taylor_green_vortex/eval_tgv.py` on 2026-09-30 22:24:15. GPU: NVIDIA GeForce RTX 4050 Laptop GPU, 6141 MiB, 595.79; 16 CPU threads. Raw data: `data/tgv_eval.json`.

## Summary

* **One Runge-Kutta stage** queues 17 loops. Adjacent-only fusion turns them into 8 kernels; the dependence DAG into 6, moving 3 loops past independent ones. Launches per iteration (including the filter steps): 51 → 24 → 18.
* **Single precision on the GPU (128³):** 20.87 ms/iteration unfused → 14.47 ms with adjacent same-range fusion (1.44×) → 13.65 ms with the DAG planner (1.53×). Most of the gain is ordinary fusion; reordering adds 6% on top. Different-range (guarded) fusion changes nothing for this app: the stage has the same kernel count with or without it.
* **Why:** the kernels are memory-bound. The byte model predicts 1.55× less traffic; the measured kernel time drops 1.55×, and the modelled bandwidth is 138 GB/s unfused against 138 GB/s fused (peak 192 GB/s). Host overhead (enqueue, planning, cache key, argument packing) is under 4% of an iteration, so cutting launches was not the gain; removing memory traffic was.
* **Double precision on the GPU** gains only 1.10× (74.82 → 68.14 ms): this GPU's fp64 rate, not memory bandwidth, is the limit, so saved traffic buys little. Single precision is 5.0× faster than double here.
* **OpenMP (8 threads, 64³):** 1.25× in single precision (34.45 → 27.52 ms) and 1.02× in double (32.70 → 32.09 ms). With all 16 threads the machine was too noisy to conclude anything (spreads up to 80%).
* **Problem size:** for N ≥ 64 the GPU speed-up is steady at 1.41–1.57×. Below that an iteration takes only 1.5–3 ms and the individual measurements scatter by more than the differences between planners, so no trend is claimed there.
* **Parameters:** a cap of 8 loops per kernel already reaches the plan's 6 kernels per stage (16 and 32 change nothing, a cap of 1 is the unfused case); the bounding-box ratio has no effect here; earliest vs. latest placement is within noise.
* **Cost:** JIT compilation of the 9 distinct queue shapes takes 6.9 s unfused and 6.1 s fused (first 100 iterations cost about 5.5 s more than steady state), a one-off equal to roughly 449 steady iterations.
* **Correctness:** all planner configurations give results bitwise identical to the unfused run, on the CPU backend and on the GPU, in both precisions (section 6). Single precision stays within about 2e-6 of double (rms, relative to the flow scale) after 26 steps.
* **What limits it:** a stage still needs several kernels. For the loops that had to start a new kernel, the planner's diagnostics count the reasons an existing kernel was rejected: `dependence` 5, `order` 1, `range` 3 (`dependence`: a stencil read of a field written in that kernel; `order`: joining would move the loop before something it depends on; `range`: the bounding-box rules). Fusing across the dependence edges would need redundant halo computation.

*Method note.* Per-iteration times come from windows of 100 iterations inside one process after warm-up. An earlier version of this evaluation differenced the wall time of a short and a long run; JIT time varies by about a second between runs, which is ±10 ms per iteration, and that method gave wrong numbers (it also counted the one-off compile of the filter kernels at iteration 25). Those numbers were discarded.
